# Phase 2, stage 2: SDRAM — waking the chip that shipped with the board

*2026-08-07 — controller done in simulation. Target: Prince of Persia, which
means 128K, which means finally using the DE10-Lite's 64 MB of SDRAM.*

## Why SDRAM now

128K needs 8×16K RAM banks. The M9K arithmetic refuses: both 128K ROMs +
128K RAM + 64K divRAM + esxDOS + line buffers ≈ 250 KB against 182 KB of
block RAM. No amount of trimming closes a 68 KB gap. The board has carried
an idle IS42S16320 (32M×16, 64 MB) since day one; the Spectrum will use
96 KB of it.

## The architectural decision: screens stay in M9K

The 128K's two screen banks (5 and 7) remain in dual-port block RAM,
exactly like today's vram: video reads one port, CPU accesses the other,
zero contention. **Video never touches SDRAM.** Consequences:

- The SDRAM controller serves exactly one master (the CPU) — no arbiter,
  no priority logic, no video-starvation analysis. The Pentagon philosophy
  survives the memory expansion.
- SDRAM holds banks 0, 1, 2, 3, 4, 6 (96 KB). CPU writes to banks 5/7 go
  to the M9K copies (whether banked at 0x4000 or 0xC000).
- M9K budget after the move: ROM48 16 + ROM128 16 + screens 32 + divRAM 64
  + esxDOS 8 + buffers ~3 ≈ 139 KB — fits, keeping the full 8-bank divRAM
  and the snapshot machinery.

## The controller (rtl/sdram.v)

Single 14 MHz domain — no CDC anywhere in the design, ever. At 71 ns per
cycle every SDRAM timing parameter is one or two cycles:

| Step | Cycles | Note |
| --- | --- | --- |
| ACTIVE | 1 | row open, tRCD = 20 ns |
| spacer | 1 | |
| READ/WRITE + auto-precharge | 1 | CL=2, burst 1 |
| data (reads) | 2 + latch | |
| **total read** | **7** | Z80 memory cycle at 3.5 MHz = 16 clocks |

Zero wait states. Byte access via the DQM lanes (byte N = word N>>1, lane
by N&1). One AUTO REFRESH scheduled every 100 cycles (7.1 µs against the
7.8 µs budget), taken when idle; auto-precharge everywhere means banks are
always closed when refresh arrives. DRAM_CLK is the inverted system clock:
commands change on our edge, the chip samples half a period later, 35 ns
of margin each way.

Verified against a behavioural model (sim/sdram_model.h) that enforces the
init ritual, tracks open rows, pipelines CL=2 reads, honours DQM on writes
and watchdogs the refresh interval: 16 checks in `make sdramtest`,
including a 20k-access soak against a shadow array at Z80 pace. Worst
refresh gap observed: 105 cycles.

## SDRAM pins (verified against two published DE10-Lite sources)

DRAM_ADDR[0..12]: U17 W19 V18 U18 U19 T18 T19 R18 P18 P19 T20 P20 R20.
DRAM_BA[0..1]: T21 T22. DRAM_DQ[0..15]: Y21 Y20 AA22 AA21 Y22 W22 W20 V21
P21 J22 H21 H22 G22 G20 G19 F22. DRAM_LDQM V22, DRAM_UDQM J21,
RAS_N U22, CAS_N U21, WE_N V20, CS_N U20, CKE N22, CLK L14.

## Next: the 128K machine itself

1. #7FFD latch: bits 2:0 RAM bank at 0xC000, bit 3 screen select, bit 4
   ROM select, bit 5 lock. Pentagon decode: A15=0, A1=0, write only.
2. Twin ROMs (ROM128_FILE parameter beside ROM_FILE), 128 editor + 48
   BASIC; the divMMC automapper sits on top of whichever is paged, as on
   any real divMMC-on-128K.
3. Memory mux: 0x4000 window = bank 5 (M9K), 0x8000 = bank 2 (SDRAM),
   0xC000 = banked (SDRAM, or M9K when 5/7 selected). Video reads bank
   5/7 per #7FFD bit 3.
4. bus_tb: paging checks (bank switch, readback isolation, screen select,
   lock bit); boot test with the 128 ROM to the menu; then the acceptance
   test this stage is named after: Prince of Persia from the SD card.
5. Keep 48K mode bit-exact: with the lock bit set (or a 48-only build
   parameter), today's 158 checks must still pass unchanged.

Timing note: frame stays 448×312 at 69888 T for now — Pentagon's own 320-
line frame is a later fidelity knob, not a Prince of Persia dependency.

## Progress log

- 2026-08-08: the 128K machine exists and Prince of Persia loads **to its
  title screen** in simulation — esxDOS boot, `.tapein`, `LOAD ""`, the
  game's own loader streaming through the tape traps into SDRAM banks.
  Fixed along the way: SDRAM glue dropped requests issued during the
  controller's 2 ms init (the 128 ROM's RAM test arrives inside that
  window; a silently-lost write read as "RAM broken" and ROM0 bailed to
  48 BASIC). Requests now wait on `ready` with WAIT holding the CPU.
- **OPEN BUG — the 128 menu never appears.** Forensics so far (ring-buffer
  M1/SDRAM/7FFD tracing in the boot harness): ROM0's RAM test passes all
  8 banks; sysvars install; the 0x5B00/0x5B14 inter-ROM trampolines work
  — two ROM0→ROM1 service calls (CHAN-OPEN at ~0x1601, PO- codes at
  ~0x0AF0) complete correctly. On the **third** call, execution appears
  in the attribute file (~0x5AF2), slides up into the 0x5B00 trampoline,
  then NOP-slides through empty RAM until a stray byte (0xEC = CALL PE)
  drops it on 0x0000 with ROM1 paged: a 48 cold boot. Suspicion: a jump
  through a channel/print vector reading a wrong value. Exonerated by
  targeted real-CPU tests: paging via #7FFD, data R/W to SDRAM, **M1
  opcode fetch from SDRAM**, CALL/RET through SDRAM, ISR-in-SDRAM at
  50 Hz — all green (cputest runs the full battery in both modes).
  Consequence: PoP's BASIC loader later dies with "4 Out of memory" —
  128 loaders lean on the ROM0-installed paging helpers at 0x5B00 that
  the crashed init never finished setting up. The menu bug is
  load-bearing and is the next debugging target.
